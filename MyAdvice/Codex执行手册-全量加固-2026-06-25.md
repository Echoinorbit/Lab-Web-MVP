### T-2.1 限流 check-and-consume 同事务 〔P0·高·P0-1 + N1（三方命中）〕
**现状**：`rate-limits.ts:89-109` 先 `upsert {count: increment}` 自增再判 `allowed`；`create-post.ts:28` 的 `checkRateLimit` 在 `:33` `$transaction` 之前；`announcements/create.ts:97-100` 同构（N1）。事务体内任一步抛错则配额已扣且无回滚。
**目标**：把「检查并消费」与业务写入放进同一事务，失败自动回滚。
**步骤**：
1. 抽象 `enforceRateLimit(tx, userId, action, max)`：事务内「先 `count` 当前窗口 → 若 `count >= max` throw 结构化超限错误 → 否则 `increment`」，用同一 `tx`。
2. `create-post.ts`/`announcements/create.ts`：删除事务外的 `checkRateLimit`，改为在 `$transaction` 内调 `enforceRateLimit(tx, …)`，置于实体写入前。
3. 保留 `RATE_LIMITS`（grad-master=5 / grad-phd=10 / advisor=无限）与返回 `remaining/max`。
**验收**：事务任一步失败时配额不被扣；连续超额第 N+1 次被拒且不消耗；并发不超卖（依赖窗口行的行锁）。
**测试**：扩展 `tests/rate-limits.test.ts`：事务失败回滚配额、超限拒绝、并发不超卖（可对 `enforceRateLimit` 注入 tx mock）。
**回滚**：恢复事务外 `checkRateLimit`。

### T-2.2 补填窗口语义原子化 〔P0·高·P0-3 / D2〕
**现状**：`backfill.ts:18-27`（读 `usedAt:null`）与 `:35-41`（`markBackfillWindowUsed`）是事务外两条独立语句；`save-report.ts:23-26` 校验窗口但**从不**标 `usedAt`，用户 24h 内反复存草稿无限编辑历史月报。
**目标**：submit 在同事务内「条件消费」窗口；明确 save 是否消耗。
**步骤**：
1. `submit-report.ts`：把窗口消费改为事务内单条条件更新，按受影响行数判定：
   ```ts
   const consumed = await tx.progressBackfillWindow.updateMany({
     where: { id: backfillWindowId, usedAt: null, expiresAt: { gt: new Date() } },
     data: { usedAt: new Date() },
   });
   if (consumed.count !== 1) throw new AppError("BACKFILL_USED", "补填窗口已使用或已过期。");
   ```
2. `save-report.ts`：与产品确认「保存草稿是否消耗窗口」。默认决策：**save 不消耗，但补填月份的 save 受窗口有效期门控**（窗口过期后即便草稿也拒绝写历史月）；在代码注释写明该决策。
**验收**：两个并发 submit 仅一个成功消费窗口；窗口过期后补填月 save 被拒；当前月正常 save 不受影响。
**测试**：扩展 `tests/progress-window.test.ts`：并发条件更新 `count===1`、过期拒绝、save 语义。
**回滚**：恢复两步式 + 事务外。
